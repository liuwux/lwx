# 随笔之一：名义上的软件需求

> 软件需求为什么常常名不副实，以及怎么让它由名变实。

## 前言

项目里有一份文档，叫“软件需求规格”。它有编号，有版本，有评审记录。可开发翻开它，看到的是这样一句话：

> 系统应快速响应语音指令。

接下来发生的事，才是真正的软件需求：某个开发者决定“快速”是三秒，“响应”是弹出一个提示，“无法识别”的时候什么都不做。这些决定没有人记录过，也没有人评审过。

文档里叫“软件需求”的东西，是名义上的软件需求；开发者脑子里和代码里那些没有成文的决定，才是实质上的软件需求。这两者之间的落差，是很多项目后期问题的源头。

（上面的场景是示意，不是对任何具体团队的描述。）

本文只想讲清楚一件事，分四步：

1. 这个落差是什么样子，会带来什么后果（第一章）；
2. 它为什么反复出现，根子在哪里（第二章）；
3. 丰田有三个想法，可以借来对付它（第三章）；
4. 具体怎么做，才能让软件需求由名变实（第四章）。

ASPICE（汽车软件过程评估模型）只在第一章出现，作为一个诊断器：它能把症状照出来，但它不是解药。
