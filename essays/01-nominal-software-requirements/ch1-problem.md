# 第一章 问题：名义上的软件需求

## 1.1 一句话里藏着多少个问题

看一个典型的式样书片段：

> 用户可通过语音设置目的地。系统应快速响应，并在出错时提示用户。

这两句话至少留下了这些问题没有回答：

- “快速”是多快？在什么硬件上、什么数据规模下？
- “响应”是什么？弹提示、播报，还是直接开始规划？
- “出错”包括哪些情况？没听清、听错了、目的地不存在、有重名、网络断了、当前正在导航？
- “提示用户”提示什么？提示多久？之后系统处于什么状态？

每一个问题都必须有答案，代码才写得出来。所以答案一定会出现，问题只在于：它出现在需求文档里，还是出现在某个人的脑子里。

## 1.2 名与实的区别

| 维度 | 名义上的软件需求 | 实质的软件需求 |
|---|---|---|
| 可验证 | “快速响应” | 在指定硬件、指定数据下，95 分位不超过 X 秒；暂时定不了的，标为“待确定”，写明谁、何时定 |
| 无歧义 | 不同人读出不同意思 | 只有一种读法 |
| 异常与边界 | 只写正常流程 | 无效输入、超时、降级、状态迁移都有交代 |
| 来源 | 不知道从哪来 | 每条能指向上层的一条需求，或者标明是派生的并写明理由 |
| 验证准则 | 没有，或者只写“测试通过” | 每条都有具体的判定条件 |
| 标识 | 一大段文字 | 每条有唯一 ID，可以被链接 |
| 责任 | 没人对质量负责 | 有人负责澄清、评审和变更 |

上面这张表是我的概括，属于“一般了解”加“个人判断”。

要注意，名义上的软件需求并不等于“写得很差的文档”。它往往编号齐全、格式规范、评审通过。它的问题不在形式，而在内容还没有做完。

## 1.3 后果链

1. **开发在编码中补全需求。** 这不可避免。
2. **补全的决定没有记录。** 只存在于代码和个人的记忆里。
3. **测试没有依据。** 测试人员按自己的理解写用例，或者直接照着实现来写，“测试通过”因此不说明“满足需求”。
4. **追溯是事后补的。** 为了应付检查，事后把需求、代码和用例对上号，链接是“凑”出来的。
5. **变更评估不了影响。** 需求一改，谁也说不清哪些设计、代码和用例要跟着动。
6. **问题在里程碑验收时集中暴露。** 此时返工的代价最高。
7. **临时指派，怨声载道。** 找个人来“补需求”“补追溯”，做的是补救，而不是纠错，同样的问题在下一个项目再来一遍。

## 1.4 ASPICE 在哪里

ASPICE（Automotive SPICE）是汽车行业评估供应商软件开发过程成熟度的模型。它的 SWE.1 讲的是软件需求分析。

按我的理解（一般了解，请以你们所用版本的过程参考模型为准，3.1 与 4.0 的过程划分有调整），它期望软件需求被明确规定、被分析、与系统需求保持一致、有验证准则、可以双向追溯，并且与相关方达成一致。

所以，名义上的软件需求，正是它想照出来的东西。它是一个好的诊断器：

- 追溯链断了，它能看出来；
- 验证准则缺了，它能看出来；
- 评审记录是空的，它能看出来。

但它不是解药：

- 它评估的是过程，不教你怎么把含糊的东西变清晰；
- 为了通过评估而补出来的材料，可能让名义上的需求看起来更像真的：编号齐了，链接有了，内容依旧是空的；
- 评估结果多少受评估师解读的影响（一般了解）。

所以本文接下来不再谈条文，而是回到问题本身：为什么没有人把名义变成实质？

## 1.5 这不是谁的错

一个常见的判断是“产品经理写不清楚”。我的看法（个人判断）是，这样说不公平。

产品经理擅长的是“做什么、为什么”，这是客户需求和产品行为层面的东西。软件需求涉及接口、异常、状态、资源约束，需要技术判断，产品经理写不清楚是正常的。

真正的问题是：这个“把产品意图转换成可实现、可验证的软件需求”的活，没有人明确负责。下一章讲这件事。
